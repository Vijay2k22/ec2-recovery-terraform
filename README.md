# Mumbai web EC2 recovery lab

Terraform creates two Amazon Linux 2023 Apache EC2 instances and a public HTTP Application Load Balancer in Mumbai (`ap-south-1`). A third EC2 instance in Hyderabad (`ap-south-2`) installs Docker and runs a rule-based Python recovery agent. The agent uses its instance profile; no static AWS keys are needed.

## Requirements

- Terraform 1.5+ and AWS credentials on **your local computer** with permission to create EC2, VPC security groups, ELB, IAM roles and policies, SNS, CloudWatch dashboards, and read AWS public SSM AMI parameters.
- A **default VPC with at least two default subnets in different AZs in Mumbai** and a default VPC/subnet in Hyderabad. The project reuses these networks. If either default VPC was deleted, create a network separately or change the Terraform data sources.
- Your account has EC2, ALB, public IPv4, CloudWatch and SNS quotas and budget for this lab.
- Outbound internet from the selected default subnets, to install Apache, pull the Python image, install boto3 and reach AWS APIs. The Hyderabad monitor's inbound SSH is restricted to your IP.
- An email inbox where you can click the SNS subscription confirmation link.

## Files

- `versions.tf`: AWS providers for Mumbai and Hyderabad.
- `variables.tf`, `terraform.tfvars.example`: inputs.
- `main.tf`, `outputs.tf`: network selection, EC2, ALB, IAM, SNS, and dashboard.
- `monitor_user_data.sh.tftpl`: installs Docker and builds/runs the agent on first boot.
- `Dockerfile`, `agent.py`: monitor image and recovery loop.

## Deploy

1. Download/unzip this project and enter the folder containing `main.tf`.
2. Copy `terraform.tfvars.example` to `terraform.tfvars`; enter your real alert email and public IP with `/32`. Optionally set an **existing Hyderabad** EC2 key pair as `key_name_hyd`. The key pair is for SSH; this template does not create it. Keep `terraform.tfvars` private.
3. Run:

```bash
terraform init
terraform plan
terraform apply
```

4. Review the plan before typing `yes`. The monitor starts itself through EC2 user data; you do **not** need to manually build and run it. Get the ALB URL, dashboard URL, and monitor IP with:

```bash
terraform output
```

5. **Confirm the AWS SNS subscription email.** Without this, no recovery emails arrive. The topic and email are in Mumbai.
6. Open the ALB URL after both web targets show `Healthy`. Open CloudWatch > Dashboards in Mumbai and choose the dashboard name in the Terraform outputs. The custom EC2Stopped metric is 0 when an instance is not stopped, and 1 when it is stopping or stopped. The dashboard uses Maximum over one-minute periods, so short events can be visible after CloudWatch ingestion. The dashboard also shows ALB healthy host count and EC2 status check metrics.

## Check the monitor

Connect to the Hyderabad monitor, then use:

```bash
sudo docker ps
sudo docker logs -f --tail 0 ec2-recovery-agent
```

If Docker is not ready, check cloud-init: `sudo tail -n 80 /var/log/cloud-init-output.log`. If the container cannot retrieve role credentials, check instance metadata hop limit 2 and the instance profile.

## Test one or both stopped instances

In the **Mumbai** EC2 console, stop `inst-1`. The agent checks about every 10 seconds. It publishes a stopped notice, requests a start, publishes a request notice, then waits for EC2 instance/system checks and ALB target health before publishing a successful recovery notice. Repeat for `inst-2`, or stop both. You can follow Docker logs and the Mumbai ALB target group status.

Subjects sent by the agent:

1. `EC2 has stopped - reason not yet determined`
2. `AI Agent identified the EC2 and requested a start`
3. `EC2 has started successfully and remains healthy`

The second subject uses the requested wording, but this implementation is a **deterministic monitoring script**, not a generative AI model. A stopped state by itself does **not** reveal whether the stop was intentional or unexpected. The first subject is therefore factual. SNS email delivery order can differ from publish order. The final subject is sent only after both EC2 checks report OK and the target group reports healthy. If recovery takes over 15 minutes, the agent publishes a needs-attention message instead. A monitor/container restart loses its in-memory pending state; this lab does not offer exactly-once notification semantics.

The dashboard's custom metrics are generated by the monitor. If the monitor is offline, custom stopped-state data stops updating; absence of a data point is not proof the EC2 is running. Standard CloudWatch graphs can have ingestion delay. This project does not diagnose the stop reason or auto-heal a running EC2 with a failed Apache service.

## Cleanup

```bash
terraform destroy
```

Review the destroy plan before confirming. Subscription emails and previously delivered messages remain in your mailbox. An SNS subscription may need to be confirmed or cleaned up manually depending on account settings.
